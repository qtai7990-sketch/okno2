# Обмен «Единое окно» — банк. Схема v2

Для службы ИБ и ИТ банка. Полная спецификация — `docs/openapi.json` (раздел `/bank/v1`).

## Принципы

- Единое окно не получает доступ к ЕСИА, ЕБС, СФР, ПОД/ФТ, РКЛ и банковским системам.
- В QR — только одноразовый непрозрачный код `OKNO1:<токен>`, срок 10 минут, одно использование. Персональных данных в QR нет.
- Банк сверяет оригиналы и проводит собственную идентификацию. Предзаполнение её не заменяет.
- Банк возвращает только нейтральные статусы. Биометрия, коды SMS, реквизиты, причины ПОД/ФТ‑решений в единое окно не передаются.
- Оператор единого окна и банк — самостоятельные операторы ПДн. Клиент даёт отдельное согласие на передачу данных именно этому банку; ссылка на него (юрлицо, версия и контрольная сумма текста, способ подписи, время) приходит банку вместе с обращением.

## Транспорт и аутентификация (всё обязательно)

1. **Отдельный адрес** банковского контура, например `https://bank-okno.<домен>.ru`. На адресе стойки банковские пути закрыты.
2. **Взаимный TLS (mTLS).** Без клиентского сертификата, выданного оператором единого окна (или выпущенного по CSR банка), соединение не устанавливается. Сервер дополнительно сверяет SHA‑256 сертификата с отпечатком, закреплённым за банком: сертификат одного банка не подходит к ключу другого.
3. **Список IP банка** на прокси.
4. **Подпись каждого запроса.** Заголовки:
   - `X-Bank-Key` — ключ API банка;
   - `X-Timestamp` — время Unix, секунды; допуск ±300 с;
   - `X-Nonce` — одноразовое значение, 16–64 символа `[A-Za-z0-9_-]`; повтор отклоняется, даже если первый запрос завершился ошибкой;
   - `X-Signature` — `hex(HMAC-SHA256(секрет, строка))`, где строка — это строки, соединённые `\n`:
     ```
     OKNO-HMAC-v2
     POST
     /bank/v1/events
     <X-Timestamp>
     <X-Nonce>
     <hex(SHA-256(тело запроса))>
     ```
     Метод и путь входят в подпись: подписанный запрос нельзя отправить на другой адрес.
5. **Ротация ключей.** Новый ключ и секрет выдаются по защищённому каналу; старые действуют ещё 24 часа.

Эталонная реализация — `tools/bank_sim.py`.

## 1. Получить обращение по QR

`POST /bank/v1/handoff/redeem`, тело `{"qr": "OKNO1:..."}`

```json
{"case_id":"…","case_number":"RYZRNB","handoff_id":"…","route":"full","services":["card","snils","ebs","sim"],
 "consent":{"recipient":"АО «…»","inn":"…","text_version":"2026-10-v1","text_sha256":"…","method":"stylus","granted_at":"…"},
 "prefill":{"surname":"…","given":"…","cyr":"…","dob":"…","sex":"M","country":"TJK","number":"…","expiry":"…",
            "migcard_series":"…","migcard_number":"…","migcard_entry_date":"…","migcard_kpp":"…","migcard_stay_until":"…"}}
```
`prefill` — только в режиме API. Ошибки: 404 — нет токена или он выпущен для другого банка; 410 — использован, отменён или истёк; 409 — нет согласия этому банку, дубль, обращение закрыто.
Погашение атомарное: из двух одновременных запросов с одним QR успешен ровно один.

## 2. Сообщить статус

`POST /bank/v1/events`
```json
{"event_id":"уникальный-в-банке","case_id":"…","handoff_id":"из ответа redeem","bank_case_id":"номер дела в банке",
 "bank_code":"код банка","occurred_at":"2026-10-01T12:00:00+03:00","schema_version":"2","note":""}
```

Проверки сервера:

| Ситуация | Ответ |
|---|---|
| Обращение передано другому банку или не существует | 403 (одинаково — перебором чужие обращения не узнать) |
| `handoff_id` не совпадает | 409 |
| `bank_case_id` отличается от ранее присланного по этому обращению | 409 |
| Услуги нет в маршруте клиента (например, SIM при пакете «только карта») | 409 |
| Нарушен обязательный порядок | 409 |
| Отказ после подтверждённой выдачи | 409 |
| Код банка не сопоставлен со словарём статусов | 422 |
| `occurred_at` без часового пояса, в будущем или раньше создания обращения | 422 |
| Повтор с тем же `event_id` и тем же телом | 200, `"status":"duplicate"` |
| Тот же `event_id` с другим телом | 409 |

Все отказы сохраняются в журнале отклонённых событий и разбираются при сверке. Состояние обращения при отказе не меняется.

**Обязательный порядок** (проверяется по подтверждённым событиям этого же банка по этому же обращению):
- `CARD_ACTIVE` — после `CARD_ISSUED`;
- `EBS_REGISTERED` — после `ESIA_CONFIRMED`;
- `SIM_CONTRACT_SIGNED`, `SIM_ISSUED`, `SIM_NOT_ISSUED` — после `ESIA_CONFIRMED` и `EBS_REGISTERED`.

**Канал СНИЛС (v0.2.8).** Если у точки банка нет полномочий на СНИЛС и подтверждение Госуслуг, администратор
переключает банк на канал «Соцфонд» (`snils_channel=sfr`). Тогда:
- события `SNILS_CREATED`, `ESIA_CONFIRMED`, `SNILS_ERROR` от этого банка отклоняются (409), СНИЛС в `services` при погашении QR не передаётся;
- предпосылку `ESIA_CONFIRMED` для `EBS_REGISTERED` и SIM‑событий заменяет шаг «СНИЛС», подтверждённый сотрудником стойки по уведомлению Соцфонда до времени события.

Предпосылка засчитывается, только если она получена раньше **и** её `occurred_at` не позже `occurred_at` текущего события (допуск на расхождение часов — 2 минуты). `bank_case_id` закрепляется первым принятым событием атомарно; отклонённое событие ничего не закрепляет.

Поле `note` принимается, но **не хранится**: персональные данные в нём передавать нельзя.

IMEI в проверку не входит: банк фиксирует IMEI в своём договоре связи (ст. 45.1 «О связи»), отметка единого окна доказательством не является.

## Словарь статусов

| Код | Смысл |
|---|---|
| BANK_CASE_ACCEPTED | Обращение принято банком |
| CARD_ISSUED / CARD_ACTIVE / CARD_NOT_ISSUED | Карта выдана / активна / не выдана |
| SNILS_CREATED / ESIA_CONFIRMED / SNILS_ERROR | СНИЛС присвоен / учётная запись Госуслуг подтверждена / ошибка |
| EBS_REGISTERED | Биометрия зарегистрирована в ЕБС |
| REVISIT_REQUIRED | Нужен повторный визит |
| SIM_CONTRACT_SIGNED / SIM_ISSUED / SIM_NOT_ISSUED | Договор связи / SIM выдана / не выдана |

## Режим «номер дела» и файл сверки

Если банк на первом этапе не подключает API: сотрудник стойки показывает номер обращения, банк сканирует оригиналы своим сканером, персональные данные из единого окна в банк не уходят. Статусы — только из **официального файла (акта) сверки банка**: `event_id`, номер обращения единого окна, номер дела в банке, код, время. Загружает администратор системы (`POST /admin/v1/banks/{id}/reconcile`) — применяются те же проверки порядка и маршрута.

Устные статусы сотрудника банка система записывает отдельно; на маршрут, KPI и вознаграждение они не влияют.

## Сверка вознаграждения

Только по принятым событиям и файлам сверки: `case_id`, `bank_case_id`, `event_id`, время, код, версия схемы, хэш тела. События хранятся без персональных данных и не удаляются вместе с обращением.
