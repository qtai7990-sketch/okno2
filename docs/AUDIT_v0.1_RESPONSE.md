## Дополнительно найдено и исправлено при проверке v0.2

- Повтор `X-Nonce` проходил, если первый запрос завершался ошибкой (откат транзакции) — nonce теперь фиксируется до обработки.
- Фиксация транзакции выполнялась после отправки ответа: при сбое базы банк получил бы «принято». Теперь ответ уходит только после фиксации.
- Пакет услуг можно было поменять после передачи в банк — теперь маршрут после передачи заморожен.
- Сканирование было возможно до согласия единого окна — теперь запрещено.
- Время событий без пояса, в будущем или раньше создания обращения — отказ.

## v0.2.6 — электронная очередь: талон в зале, табло, поясной принтер

Решение заказчика: сотрудник в зале выдачи багажа выдаёт клиенту бумажный талон (номер + QR) с поясного принтера;
клиент поднимается в офис, ждёт вызова на табло с голосовым объявлением; оформление — только в офисе.

- **Сервер:** модель `Ticket` (без персональных данных: номер, язык, время, статус, стойка), миграция `0002_queue`
  (проверено: `alembic upgrade head` + `alembic check` без расхождений, `downgrade 0001` и обратно).
- **Роли устройств:** `hall` (только выдача талонов), `reception` (приём, талон без зала, обзор), `desk` (всё), `board`
  (только табло, вход сотрудника запрещён). Ограничение — по списку путей в зависимости `operator`.
- **Номер талона:** серия устройства (буква из `ABEKMHPCTX`, совпадают в латинице и кириллице) + порядковый номер за день;
  номер — атомарный счётчик `ticket_counters` (UPDATE … RETURNING), плюс уникальность `(stand_id, day, number)`;
  на PostgreSQL 20 одновременных выдач с одного планшета — 20 разных номеров. QR — 16 случайных цифр, в базе хэш.
- **Очередь по приходу в офис**, не по номеру. Вызов — атомарный захват `UPDATE … WHERE status='waiting'`:
  два рабочих места не получат одного клиента (тест с 6 параллельными вызовами).
- **Жизненный цикл:** issued → waiting → called (повтор вызова, «не подошёл» → noshow, повторная регистрация — в конец)
  → serving (открывается обращение, `case.ticket_id`, язык из талона) → bank (вызов к окну банка только после передачи
  в банк) → done (при закрытии обращения). Талон другого дня не принимается.
- **Табло** `web/board.html`: номер → стойка/окно банка, сигнал WebAudio и русский голос `speechSynthesis`;
  объявление только новых вызовов (id + счётчик вызовов). Ключ табло хранится в браузере — он даёт только номера.
- **Печать:** `TicketPrinter.kt` — Bluetooth Classic SPP, ESC/POS `GS v 0` растром полосами по 128 строк; талон рисуется
  в интерфейсе картинкой (таджикские и киргизские буквы не зависят от кодовых страниц принтера). Разрешение
  `BLUETOOTH_CONNECT` (Android 12+), `BLUETOOTH` до API 30. Новых зависимостей нет — lockfile не меняется.
- **Отчёт очереди:** выдано, пришли, обслужены, «не подошли», среднее и максимальное ожидание, по часам, по языкам,
  по сотрудникам зала (выдал / дошли / обслужены).
- Добавлен киргизский язык (`ky`): талон, выбор языка объяснения согласия, автоопределение по MRZ `KGZ`.
  Памятки на киргизском нет — показывается русская с пометкой.
- Отдельная проверка кода (независимый рецензент) нашла 7 замечаний, все исправлены: табло не зависит от проверки версии приложения; чужой вызов другая стойка не трогает; «Клиент подошёл» — атомарно; номера стоек уникальны; вызов к банку после закрытия обращения запрещён; время отдаётся с часовым поясом; соединение с принтером закрывается в потоке печати.
- Тесты: 54 (было 39). Проверено в браузере: зал → талон (картинка талона 576 и 384 точек), стойка → приём → вызов,
  табло, открытие обращения с номером талона. Kotlin — компиляция против заглушек Android API.
- **Не проверено здесь:** печать на живом принтере и сборка APK (GitHub). Переводы талона — черновые, до выхода к людям
  проверить носителем языка.

  даёт тот же QR, в базе по‑прежнему только хэш.
- **P0‑3 принтер.** Рабочая сборка печатает только на принтер из управляемой конфигурации MDM (`printer_mac`,
  `printer_dots`, `printer_name`); выбор в приложении — только в учебной сборке и только если MDM принтер не задала.
- **H‑1, H‑2** README и DEPLOY: версии, число тестов, фактическая схема печати. **H‑3** `versionName` = `0.2.7+<сборка>`.
  **H‑4** позиция в очереди при равном времени прихода учитывает порядковый номер — как при вызове.
- Из схемы Manus: пометка на талоне «Талон электронной очереди офиса. Не является документом аэропорта»; фраза на языке
  клиента на табло (записанные файлы tj/uz/ky, без номеров — номер звучит по‑русски и виден на табло); автоповтор вызова
  к стойке через 40 с, не больше двух раз; проверка датчика бумаги `DLE EOT 4` перед печатью; отметка «напечатан».

**Не согласен**
- **P0‑1 «нет lockfile — сборка упадёт».** Это заложено: lockfile создаёт GitHub в workflow «Фиксация зависимостей
  Android» (шаг 2 плана партнёра), здесь Google Maven недоступен. Без этого шага сборка останавливается намеренно.
- **P0‑4 «ZIP без .git».** Архив — способ передачи на проверку по решению заказчика; репозиторий создаётся из архива по
  плану (закрытая организация, правила ветки и тегов). Это не дефект кода.
- **«Принтер отказал — выдачу остановить».** Номер остаётся на экране планшета, клиент фотографирует; в очередь талон попадает
  только после сканирования в офисе, ложной очереди нет. Остановка выдачи во время прилёта — потерянные клиенты.
- **SDK Epson/Zebra.** Не нужен: ESC/POS через SPP понимают почти все чековые принтеры; Epson и Zebra ушли из РФ.
- **«QR талона — не доступ к банковскому делу».** Так и есть с v0.2.6: QR талона — только очередь; банку выдаётся отдельный
  одноразовый код `OKNO1:` после согласия клиента на передачу данных этому банку.

- Тесты: 58. Проверено в браузере: зал → талон (с пометкой), стойка, табло: фраза на языке клиента запрашивается,
  автоповтор через 40 и 80 с. Kotlin — компиляция против заглушек Android API.
- Отдельная проверка v0.2.7 (5 замечаний, исправлены): новые поля талона вынесены в отдельную миграцию `0003`
  (база на `0002` обновляется, проверено на SQLite и PostgreSQL вверх‑вниз); соединение с принтером переиспользуется только
  с тем же адресом — смена принтера в MDM действует сразу; ключ QR выводится из ключа шифрования данных (он не меняется),
  а не из ключа дублей; объявления на табло идут строго по очереди, записи автоповтора очищаются; тест одновременных
  запросов с одним ключом требует успешного ответа от каждого.
